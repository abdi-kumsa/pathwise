Section 1

What is PathWise?

PathWise is a web application — meaning it runs in a browser, like a website — built specifically for a university or educational institution. It has two parts, called dashboards, that answer two important questions the institution currently cannot answer well.

It is not a chatbot. It is not a search engine. It is closer to a custom analytics platform — think of it like Power BI or Google Analytics, but built from scratch, specifically for this institution, and powered by AI models trained on their own data.

One sentence summary: PathWise is a custom-built AI-powered analytics platform that helps university administrators make smarter decisions about student enrollment and graduate employment.

Who uses it?

  • University administrators — to decide how many students to admit and into which programs
  • Department heads — to understand whether their curriculum matches what employers actually need
  • Students — to check their own placement readiness and get skill recommendations
Section 2

The Two Problems It Solves

Problem 1 — The Employment Gap

Universities produce graduates, but they often do not know clearly: which companies are hiring, for which roles, requiring which skills, at what salary. They make curriculum decisions based on outdated information or guesswork. Meanwhile students graduate without the skills the market actually wants.

PathWise fixes this by pulling in real job posting data, analysing it with AI, and showing administrators exactly where demand is, what skills are trending, and which graduates are most employable — and why.

Problem 2 — The Enrollment Guessing Game

Every year, a university has to decide: how many students to admit, into which programs, at what capacity. Too many students and not enough jobs waiting for them is bad. Too few students means missed tuition revenue and underused resources. Most institutions use spreadsheets and gut feeling to make this call.

PathWise fixes this by using AI to analyse historical enrollment patterns, labor market trends, and economic signals — then forecasting the right intake numbers with confidence intervals, not guesses.

Section 4

Technical Terms Explained

Every term below is something that may come up in the meeting. Read through each one so you can respond confidently if the client asks.

XGBoost
Extreme Gradient Boosting

An AI model that is very good at looking at a table of data and learning patterns from it. You give it thousands of rows of past student data (GPA, internships, projects, outcome) and it learns which combinations of factors lead to placement and which don't.

Once trained, it can look at a new student's profile and predict: "This student has a 72% chance of getting placed." It is the engine behind the Placement Probability Evaluator.

Think of it like a very smart pattern-recognition system that has studied thousands of past cases and can now make predictions on new ones.

"We use XGBoost for the placement prediction model — it's an industry-standard machine learning algorithm that learns from historical student data to score new students in real time."
LSTM
Long Short-Term Memory

An AI model specifically designed to understand sequences of data over time — like enrollment numbers year by year. It has a kind of "memory" so it doesn't just look at last year's number, it considers the full trend over many years.

You give it 10 years of enrollment data and it figures out the growth pattern, the seasonal patterns, the cycles. Then it predicts the next 1–3 years. It powers the Enrollment Forecast chart.

Think of it like a model that has read a university's full history and can now say: "Based on everything I've seen, next year's intake in Computer Science will be around 340 students."

"LSTM is a deep learning model we use for time-series forecasting — it captures long-term patterns in enrollment data to produce accurate intake predictions."
Prophet
Open-source forecasting tool by Meta (Facebook)

Another forecasting model, like LSTM, but simpler and faster to set up. Also used for predicting numbers over time. We use both Prophet and LSTM for the enrollment forecasts — Prophet as a quick, reliable baseline and LSTM for more complex pattern detection.

Think of it as a second AI giving a second opinion on the enrollment forecast. If both agree, the prediction is more trustworthy.

"We run Prophet alongside LSTM for our enrollment forecasts — having two independent models cross-check each other increases the reliability of the predictions."
SHAP
Shapley Additive Explanations

This is not a forecasting model — it's an explainability tool. AI models can sometimes feel like a black box: they give you an answer but don't tell you why. SHAP fixes that.

When the model says "this student has a 65% placement chance", SHAP also shows: "GPA is helping (+15%), internship count is helping (+22%), but low project count is hurting (-12%)." It makes the AI transparent and trustworthy.

"SHAP gives us explainability on top of our models — so administrators and students don't just get a score, they see exactly which factors drove that score."
API / FastAPI
Application Programming Interface

An API is a messenger between two software systems. In PathWise: the AI models live on a server, and the dashboard lives in the browser. They need a way to talk to each other. The API is that communication layer.

FastAPI is the specific tool we use to build that messenger. When a user opens the Placement Evaluator and types in their GPA, FastAPI receives that request, passes it to the XGBoost model, gets the score back, and sends it to the dashboard to display.

"FastAPI is our backend API layer — it handles all communication between the AI models and the user interface, and it auto-generates documentation for every endpoint."
PostgreSQL
A relational database system

This is where all the data is stored — student records, job postings, enrollment history, placement outcomes. PostgreSQL is a database, similar in concept to Excel but far more powerful, structured, and secure.

It runs on a server. The API talks to it to read and write data. The ML models were trained on data that came from it.

"We use PostgreSQL as our database — it stores all student, enrollment, job posting, and placement data, and it's designed for the kind of analytical queries our dashboards run."
React
A JavaScript framework for building web UIs

React is the tool used to build what the user sees — the dashboards, the charts, the navigation, the forms. It is the industry standard for building modern, interactive web applications. Developed by Meta (Facebook).

It handles things like: when a user clicks a filter, the charts update instantly without reloading the page. When the API returns new data, the dashboard refreshes automatically.

"The frontend is built in React — it's a modern single-page application with live API integration and interactive charts via Recharts."
Docker / Docker Compose
Containerisation and orchestration tools

Docker packages the entire application — the database, the API server, the frontend — into containers that run the same way on any computer. This means the app works identically on a developer's laptop, a test server, and a production server.

Docker Compose is the tool that starts all three containers together with one command. Instead of manually starting the database, then the API, then the frontend separately, you run one command and everything starts.

"The entire stack is containerised with Docker Compose — one command spins up the database, API, and frontend together, making deployment straightforward."
ETL Pipeline
Extract, Transform, Load

This is the process of taking raw data from wherever it lives (CSV files, external systems, scraped sources), cleaning it and reshaping it, then loading it into the database.

Extract = pull the raw data. Transform = clean it, fix errors, calculate new columns. Load = put it into the database. This has to happen before any AI model can train.

"We have a full ETL pipeline that ingests raw data sources, cleans and feature-engineers them, and loads them into PostgreSQL ready for model training and live queries."
Feature Engineering
Preparing data to make AI models smarter

Raw data is not ready for AI models as-is. Feature engineering is the process of creating new, smarter columns from the raw data that help the model see patterns more clearly.

For example: instead of just giving the model "enrollment was 300 in 2023", you also add columns like "enrollment 1 year ago", "enrollment 3 years ago", "average over last 3 years", "percentage change from last year". These extra columns — called features — give the model context and memory.

"Feature engineering is a critical step in our pipeline — we enrich the raw data with lag values, rolling averages, and seasonality signals before it reaches the models."
ORM Models
Object-Relational Mapping

The database stores data in tables. The Python backend code works with objects. ORM is the layer that maps one to the other — so instead of writing raw SQL database queries, the code can work with Python objects and the ORM translates that to database operations automatically.

SQLAlchemy is the specific ORM tool used in PathWise. It makes the code cleaner, safer, and easier to maintain.

"We use SQLAlchemy ORM models — they give us a clean, type-safe interface to the database from Python, without writing raw SQL."
MAE / RMSE / MAPE
Model performance metrics

These are numbers that measure how accurate the AI models are. After training, you test the model on data it has never seen and measure how far off its predictions are.

  • MAE (Mean Absolute Error) — average size of the prediction error
  • RMSE (Root Mean Square Error) — similar but penalises large errors more heavily
  • MAPE (Mean Absolute Percentage Error) — the error expressed as a percentage

Lower numbers = better model. We track these continuously to know when a model needs retraining.

"We evaluate model performance using MAE, RMSE, and MAPE — and we have a monitoring pipeline that tracks these metrics over time to flag when retraining is needed."

The one sentence that covers the whole architecture: "Raw data goes in one end, gets cleaned and prepared, gets fed to AI models, the models' predictions are served through an API, and the dashboards display those predictions as interactive charts for decision-makers."

Why is the API in the middle?

The AI models live on a server — they are heavy files that run Python code. The dashboard lives in a browser. A browser cannot directly run a Python AI model. The API is the bridge: the dashboard asks the API for an answer, the API runs the model and returns the result, the dashboard shows it to the user. This is standard architecture for any web-based AI product.

Why Docker?

The system has three separate programs running: the database, the API server, and the frontend web server. They all need to run together. Docker packages each one independently so they work on any machine, and Docker Compose starts all three with a single command. This makes deployment and future handoff simple.

Section 10

What Is Coming Next — Phase 2

Phase 2 is the Data Pipeline. Three scripts will be written:

1. generate_mock_data.py

This script creates realistic fake data using a tool called Faker. It will generate thousands of fake student profiles, job postings, enrollment records, and placement outcomes. The data will look and behave like real institutional data but is entirely synthetic — no real students or companies involved.

2. load_to_db.py

This script takes the generated CSV files and loads them into the PostgreSQL database. It handles the Extract → Transform → Load process: reads the files, validates and cleans the data, then inserts it into the correct tables.

3. feature_engineering.py

This script takes the raw loaded data and builds the enriched feature columns the AI models need — lag values, rolling averages, seasonality flags. It saves the output as parquet files (a fast, compressed format for large data) that the ML models in Phase 3 will train on.

Important question for the client meeting: Will the client provide real institutional data (enrollment records, placement history, job feeds), or should synthetic data be used for the full build? Either works — but the answer needs to be confirmed now so Phase 2 is built correctly. If real data, it must arrive by Week 5.
